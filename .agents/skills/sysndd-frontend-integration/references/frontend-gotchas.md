# Frontend gotchas: tables, tags, review forms, ClinVar, Playwright

> Extracted verbatim from `AGENTS.md` (2026-09-01) to keep the root instruction file lean.
> This is the authoritative detail for these rules.

- ClinVar `clinical_significance` is a controlled vocabulary and MUST be classified by **exact string equality** against the shared lookup table — never `includes()`/`grepl()`. `"Conflicting classifications of pathogenicity"` contains the substring `pathogenic`, which is how it was counted and drawn as **Pathogenic** across the lollipop, gene-structure plot, 3D viewer and variant panel while the server-computed ClinVar card on the same page disagreed (#607: PCDH12 showed `Pathogenic 46` next to `P 18`). The single client source of truth is `app/src/types/clinvarSignificance.ts` (`normalizeClinVarSignificance()`); `protein.ts::normalizeClassification()`, `alphafold.ts::classifyClinicalSignificance()` and `GeneClinVarCard.vue` are thin adapters over it, and `normalize_clinvar_classification()` in `api/functions/external-proxy-gnomad-clinvar.R` mirrors the same table. All three are driven in test by one fixture, `api/tests/testthat/fixtures/clinvar-significance-vocabulary.json` (loaded on the TS side by `app/src/test-utils/clinvarVocabularyFixture.ts`) — add a new term **there first**, then to both tables; both suites assert their table's key set equals the fixture's in **both directions**, so neither can drift. ClinVar **aggregate** values (`Pathogenic/Likely pathogenic/Pathogenic, low penetrance/Established risk allele; risk factor`) are resolved by parsing ClinVar's documented delimiter grammar — first `;`/`|` segment, split on `/`, exact-match **every** token — where one unresolvable token poisons the whole value; whole-string matching alone would send those to unknown and **undercount** real pathogenic variants. Anything still unresolved is `unknown` (client) / `other:<sanitized>` (server), is logged once per distinct term, and must never reach an ACMG tier. `conflicting` is a first-class class on both sides: `counts$conflicting` + `class_breakdowns$conflicting` on `/api/external/gnomad/variants/<symbol>?summary=true` (declared **optional** on the TS wire type so a pre-#607 payload zero-fills instead of rendering `undefined`), and its own purple (`#6f42c1`, the `$purple` token value) legend chip on all three visualizations plus a `CONF` chip on the card. Both plots keep their P/LP-only default, so Conflicting and Other default to hidden there with their counts on the chip; the 3D panel shows everything, so Conflicting shows. `PATHOGENICITY_SEVERITY` ranks `other` **lowest** — it previously ranked highest, so one unrecognised variant hijacked the dominant colour of an aggregated position — and `pathogenicitySeverityRank()` is the one ranking used by both aggregated and individual lollipop rendering (they were separate maps that already disagreed).
- Review phenotype and variation tags are encoded as `<modifier_id>-<ontology_CURIE>` — for example `1-HP:0001249` and `5-VariO:0015`. They originate from the review subresource API rows (`/api/review/<id>/phenotypes` and `/api/review/<id>/variation`) and the `/api/list/phenotype?tree=true` / `/api/list/variation_ontology?tree=true` option ids. CURIE ids are strings, never numeric; exclusively use `splitOntologyTag()` to parse them, which splits only at the first separator so suffixes such as `CURIE:part-with-hyphen` remain intact.
- A review-form composable must submit the curator's **live** selection, never a union with the set it loaded. `useReviewForm.submitForm()` merged `originalPublications ∪ formData.publications` as a "never accidentally delete an existing publication" guard; because `publication_replace_for_review()` (`api/functions/publication-repository.R`) is an honest DELETE-then-INSERT of exactly what it is sent, that union made **removal impossible** on the one surface that had it — the chip vanished, the PUT returned 200 with "Review submitted successfully", and the row came straight back (#635). The two sibling surfaces that also prefill-and-resubmit publications (`views/curate/composables/useEntityInfo.ts` for Modify Entity, `composables/review/useReviewApprovalActions.ts` for Approve Review) never had it, which is exactly why removal worked from Modify Entity and nowhere else. A guard that cannot distinguish "the curator cleared the field" from "a hypothetical reactivity failure" is not a guard; if a desync is ever observed, fix the binding. De-duplicate the current selection (`new Set(formData.publications)`) — do not re-derive it from a loaded snapshot.
- `Review.vue`'s create-vs-update decision must come from `useReviewForm`'s own `reviewId`, never from `review_info.review_id`. `useReviewData.loadReviewInfo()` catches its errors, calls `reportError()` and returns, and `infoReview()` then opens the modal anyway — so a failed or empty metadata fetch left `review_id` null, flipped `isUpdate` to `false`, and made the save POST `/api/review/create`, minting a **second review** for an entity that already had one (with its publications INSERTed onto the new row instead of replacing those on the old). `loadReviewData()` is atomic by contrast: a rejection propagates out of `infoReview()` before `show()`, so whenever the modal is open its `reviewId` is the id it was opened with. Guard: `app/src/views/review/Review.submitMode.spec.ts`.
- The Playwright baseline's publication row must stay **production-shaped**: `publication_id` carries the `PMID:` prefix and `publication_type` is `additional_references` | `gene_review`, in **both** `publication` and `ndd_review_publication_join`. It was seeded `'12345678'` / `'PMID'`, which matches neither filter in `useReviewForm.loadReviewData()` — so the row rendered as no chip at all and #635 shipped without end-to-end coverage. Production holds only those two types (join table 8148 / 1099; `publication` 4304 / 386; zero of anything else).
- In a Playwright spec, match a `BFormTag` chip by its **text**, never by `[title="…"]`. `BFormTag` renders `title` from its own internal `tagText`, and `ReviewFormFields.vue` fills the tag's default slot with a `<BLink>` rather than a bare string, so the attribute is the literal `"[object Object]"`. The remove control is `.b-form-tag-remove`. Scope to a specific tag widget through the id its inner input carries (`#review-literature-select` for Publications, `#review-genereviews-select` for GeneReviews) — the label's `for="review-publications-select"` does not match any element.
- BootstrapVueNext `BTable` (and the `GenericTable` wrapper) cannot display a field whose `key` contains a dot: its cell value resolver renders a blank cell, and Vue also parses a `#cell-a.b` slot name as `cell-a` + a `.b` modifier, so neither the column nor a custom cell slot can show the value. When source data has dotted column names (e.g. the MCA stats `p.value`, `v.test` from the phenotype-clustering snapshot), alias them to flat keys (`p_value`, `v_test`) before binding them as field keys — see `normalizePhenotypeClusterRows()` in `app/src/components/analyses/phenotypeClusterTable.ts` (regression-guarded by its spec and `AnalysesPhenotypeClusters.spec.ts`). Keep the original dotted keys on the row if other consumers (e.g. the Excel export header map) still read them.
- BootstrapVueNext's `v-b-tooltip` directive is only reactive to its **binding value**, not to a bound `:title` attribute. `hasBindingChanged()` compares `JSON.stringify([binding.modifiers, binding.value])`, so once the floating popover element exists, changing a reactive `:title` patches `data-original-title` but never re-renders the popover body. Faceted-table column headers (Entities/Genes/Phenotypes/PubtatorNDDGenes/CurationComparisons) bind the distinct-count tooltip through the directive **value** — `v-b-tooltip.hover.bottom="getTooltipText(field)"`, never `:title="getTooltipText(field)"` — so the "unique filtered/total" counts update when a filter changes `count_filtered`. Symptom of the bug: tooltip shows the global `count/count` (e.g. `4200/4200`) after an interactive filter instead of `count_filtered/count` (`1997/4200`); it only looked right on a fresh page-load because the popover was created once with the already-filtered value. Static guard: `app/src/components/tables/columnHeaderTooltipReactivity.spec.ts` (exercises the real bvn directive both ways). Static `:title` tooltips (e.g. NddScoreGeneTable column help, ReviewTable header label) are unaffected because their text never changes.
- Genes / Entities detail pages (v11.3) use an in-house SWR composable layer (`app/src/composables/useResource.ts` + Pinia `cacheStore`) and ~12 per-source hooks. Each card on the page is a `<SectionCard>` with skeleton + hide-when-empty. `<TablesEntities>` mounts on the URL-derived filter (HGNC id or symbol) — no gating on the gene record. There is a Playwright perf + axe bench at `app/tests/perf/genes-entities.bench.spec.ts` (local-only). Historical design docs are archived at `.planning/_archive/superpowers/specs/2026-04-26-v11.3-genes-entities-perf-ux-design.md` and `.planning/_archive/superpowers/plans/2026-04-26-v11.3-genes-entities-perf-ux-plan.md`.
- Modify-path direct approval (`ModifyEntity.vue`) mirrors the entity-create `direct_approval` flow. `POST/PUT /api/status/create|update` and `/api/review/create|update` accept `?direct_approval=true`; the handler escalates the role gate to **Curator** before approving (Reviewer callers requesting direct approval get 403) and reuses `svc_approval_status_approve` / `svc_approval_review_approve` (via `svc_status_apply_direct_approval` / `review_apply_direct_approval` in `api/services/approval-service.R`) so the sibling-reset semantics match the `/approve` endpoints. Never trust the client flag — it is re-checked server-side. The frontend gates toggle visibility with `useAuth().hasMinRole('Curator')` (hierarchy-aware: Administrator passes; unlike the exact-match `hasRole`). The combined Status & Review modal (#36) submits review-before-status via `useCombinedStatusReview`; the view stays a thin shell by delegating to `useModifyEntityWorkflows` / `useModifyEntityLookups`.
