# Variation-ontology provenance (#608)

> Extracted verbatim from `AGENTS.md` (2026-09-01) to keep the root instruction file lean.
> This is the authoritative detail for this subsystem.

Every variation-ontology annotation can state where it came from, and a machine-derived annotation can no longer become curator-authored without an explicit act. Migration `047_add_variation_ontology_provenance.sql` adds two additive tables — `variation_ontology_assertion` (one row per annotation identity, carrying `state` ∈ `suggested`/`active_unconfirmed`/`confirmed`/`rejected` plus `confirmed_by`/`confirmed_at`/`rejected_reason`) and `variation_ontology_evidence` (one row per source batch, with `evidence_summary` as a **stored column**, a 0–4 `evidence_strength`, and the full payload in `evidence_json`) — and bumped the manifest in `api/functions/migration-manifest.R` at the time. Later migrations have moved it on since; read the current `EXPECTED_LATEST_MIGRATION` / `EXPECTED_MIGRATION_COUNT` values there rather than trusting any number quoted in prose.

- **Absence of an assertion row means curator-authored.** That is the whole contract, and it makes two things true at once. (a) With zero assertion rows the feature is **inert**: `GET /api/entity/<id>/variation` returns `provenance: null` for every term and the public Variation Ontology card renders exactly as it did pre-#608 — no legend, no glyph, no affordance, no claim (locked by `EntityEvidenceGridProvenance.spec.ts`'s golden-HTML assertion and by the endpoint tests, not by inspection). (b) Provenance **means nothing until the backfill completes**. The backfill lives in the companion `sysndd-administration` repo and covers all three February 2026 import batches (182 + 5,763 + 2,166 = 8,111 annotations). A *partial* backfill is worse than none: it would positively present the un-backfilled batches as curator-authored, inverting the feature's primary goal (spec §7.1 release gate). The write-side fix below is the opposite — ungated and valuable immediately, because every review saved without it makes one more entity permanently ambiguous.
- **Provenance is deliberately NOT a column on `ndd_review_variation_ontology_connect`.** `variation_ontology_replace_for_review()` (`api/functions/ontology-repository.R:233`) handles every review edit as `DELETE FROM ndd_review_variation_ontology_connect WHERE review_id = ?` followed by a re-`INSERT` of each submitted term, so a provenance column on that table would be destroyed on **every** review save. This feature never alters that table and never writes it outside the two sanctioned repository functions (`variation_ontology_connect_to_review()` / `variation_ontology_replace_for_review()`).
- **Identity is `(entity_id, vario_id, modifier_id)`. Never key on `(entity_id, vario_id)`.** `modifier_list` seeds both `present` (1) and `absent` (5) with `allowed_variation = 1` (`db/migrations/000_initialize_base_schema.sql:488-493`) and the connect table's own unique key is `(review_id, vario_id, modifier_id, entity_id, is_active)` (`:422`). "Missense is present" and "missense is absent" are two different claims with independent state, so `uq_assertion` is `(entity_id, vario_id, modifier_id)` and every join, cache key and UI `data-tag` carries the modifier.
- **The identity comparison is case-normalized.** `.variation_provenance_identity_key()` (`api/functions/variation-provenance-reconcile.R`) upper-cases `vario_id` and integer-coerces `modifier_id` on **both** sides of every comparison. The reachable failure this guards is the backfill direction: `variation_ontology_list.vario_id` collates case-insensitively, so if the administration-repo backfill stores a non-canonical casing, a case-sensitive R comparison would find no match, treat every backfilled assertion as **omitted**, reject it, drop it out of the read path's `state IN ('active_unconfirmed','confirmed')` filter — and the still-served term would then read as curator-authored, the exact fabrication this feature exists to prevent. (The originally reported *submission*-side attack path is **not** reachable: `review_write_validate_lookup_ids()` compares with R's case-sensitive `setdiff()` and 400s a case variant before reconciliation runs. Keep the normalization anyway; it is the backfill direction that matters.)
- **Migration 047 derives `vario_id`'s charset/collation from `information_schema.COLUMNS` at migration time** and interpolates it into dynamic `CREATE TABLE` DDL, falling back to `utf8mb3`/`utf8mb3_general_ci` only when the lookup yields nothing. Do **not** "simplify" this back to a static `DEFAULT CHARSET=utf8mb3`: the referenced `variation_ontology_list.vario_id` is not reliably `utf8mb3` (observed live in this repo's own `sysndd_db_test` as `utf8mb4`/`utf8mb4_0900_ai_ci`), and a mismatched referencing column makes MySQL refuse the FK with "Referencing column ... and referenced column ... in foreign key constraint ... are incompatible". Same family as the documented `disease_ontology_mapping` collation trap. Only `vario_id` needs it — the other three FKs are on `INT` columns. Because the DDL is dynamic anyway, ENUM/CHECK string literals inside the `CONCAT()` pieces use **escaped single quotes** (`''`), not double quotes, so the migration still applies under a `sql_mode` including `ANSI_QUOTES`.
- **Write reconciliation is the load-bearing fix**, and it is server-side. `variation_provenance_reconcile_for_review()` runs inside `review_write_mutate()` (`api/services/review-write-service.R`) on the **same `txn_conn`** as the connect-table write and immediately after it, so state transitions commit or roll back with curated membership. Architecture is a **pure planner** (`variation_provenance_plan_reconciliation()` — no SQL, no side effects) plus a **thin applier** (`variation_provenance_apply_reconciliation()` — one `UPDATE` per planned transition, no transaction of its own). The state machine, which the module header carries verbatim:

| Submitted? | Previous state | `provenance_action` | New state | Attribution |
|---|---|---|---|---|
| yes | `active_unconfirmed` | absent / not `"confirm"` | `active_unconfirmed` (unchanged) | — |
| yes | `active_unconfirmed` | `"confirm"` | `confirmed` | `confirmed_by`/`confirmed_at` |
| yes | `suggested` | any | `confirmed` | `confirmed_by`/`confirmed_at` |
| yes | `confirmed` | any | `confirmed` (unchanged) | **never re-stamped** |
| yes | `rejected` | any | `confirmed` | `confirmed_by`/`confirmed_at` |
| yes | (no assertion row) | any | no row created — curator-authored | — |
| no | `active_unconfirmed` | — | `rejected` | — |
| no | `suggested` | — | `rejected` | — |
| no | `confirmed` | — | `confirmed` (unchanged) | — |
| no | `rejected` | — | `rejected` (unchanged) | — |

Row 1 is the fix: a curator who saves without engaging a pre-checked machine-derived term leaves it unconfirmed — the annotation stays live, it is simply never silently upgraded. Only transitions where `to_state != from_state` are returned, so the applier can never issue a pointless `UPDATE` or re-stamp a historical confirmation. `VARIATION_PROVENANCE_CONFIRM_ACTION` is the only value that confirms; anything else (absent, `NA`, another verb, another capitalisation) falls through to "no action", fail-closed. `variation_provenance_assertions_for_entity()` is deliberately **unfiltered by state** — the machine needs the `suggested`/`rejected` rows to lift them back to `confirmed`. An **unparseable** submitted set raises `variation_provenance_unparseable_input` rather than degrading to zero rows, because "empty" drives rejection and a module whose purpose is to stop fabricated provenance must not fail toward destroying it. The call in `review_write_mutate()` is deliberately **not** `exists()`-guarded: a missing module must fail loudly rather than silently skip reconciliation and restore the bug.
- **Rejection scope — read this before "fixing" it back.** Confirmation transitions **always** apply, on a draft save exactly as on an approved one. **Rejection** transitions (rows 7 and 8) apply only when the save actually determines the entity's served term set, computed by `review_write_save_determines_served_set()` (`review-write-service.R`) as `direct_approval == TRUE`, **or** the just-written review row being `is_primary = 1 AND review_approved = 1` (read on `txn_conn` so it observes this transaction). Why: assertions are entity-scoped, but the publicly served terms come from the **primary approved review**, so a Reviewer's draft POST that omits a term — or omits `variation_ontology` entirely, which `prepare()` normalizes to a zero-row set and so omits *everything* — is not a statement about the served set. Without this, a draft save would reject every assertion for the entity while the approved review kept serving those very terms, and they would render as curator-authored; rows 9/10 make the omitted branch terminal, so an abandoned draft would suppress provenance permanently. This **departs from the literal reading of the design spec's §5.3 row 3**, which mandates the unconditional rejection: on this input the spec contradicts itself, and its primary goal (a machine-derived annotation never becomes curator-authored without an explicit act) governs. Deferring rejection is also more faithful to row 3's stated purpose — removal becomes real when it becomes public. Note that `review_update()` unconditionally sets `review_approved = 0` (`api/functions/review-repository.R:258-263`), so the `is_primary AND review_approved` branch never fires through a normal PUT save today; `direct_approval` is the operative branch. Known residual: **edit-then-approve-separately never rejects**, because reconciliation runs on write, not on approval (safe direction — the term stops being served anyway).
- **Rename reads its source snapshot INSIDE the write transaction, under a row lock (#640).** `svc_entity_rename_load_source()` (`api/functions/entity-rename-source-snapshot.R`) is called from within `db_with_transaction()` on `txn_conn` and opens with `SELECT review_id FROM ndd_entity_review WHERE entity_id = ? FOR UPDATE`. The five copy-forward reads used to run on the pool BEFORE the transaction, so an approved review write committing in that window was copied over and silently discarded — and post-#612 it could put a still-served connect row (stale read) beside a `rejected` assertion (fresh read) on the new entity, which the public read then renders as **curator-authored**. Reading inside the transaction is necessary but NOT sufficient on its own: InnoDB's REPEATABLE READ snapshot is taken at the first read while writes see the latest committed rows, so only the locking read closes the window. It locks **every** review row of that one entity, not just `is_primary = 1`, because an approval can change which row is primary. This is not the contention migration `049` avoided — that was a shared parent-row lock taken once per each of ~8,083 evidence rows in a bulk backfill; this is a handful of rows for a single entity during a rare interactive action. The friendly "no active status" **409 precondition stays OUTSIDE** the transaction on purpose: `db_with_transaction()` re-raises every error as `db_transaction_error`, flattening the class, so an abort raised inside cannot be mapped back to a 409 without changing that shared helper for every caller.
- **Rename carry-forward.** `svc_entity_rename_full()` (`api/services/entity-rename-service.R`) creates a brand-new `entity_id` and copies the entity's curated variation-ontology connect rows onto it. Assertions are keyed on `entity_id`, so without a carry-forward the renamed entity's copied terms would all read as curator-authored the instant they landed — a rename relocates rows, it is **not** an act of confirmation. `variation_provenance_carry_forward_entity()` (`api/functions/variation-provenance-carry-forward.R`, extracted from the reconcile module so both stay under the 600-line ceiling) is called inside the rename transaction on the same `conn`. It is a verbatim **COPY**, not a move (the old entity may still be referenced via `ndd_entity.replaced_by`), takes no "acting user" argument at all so it cannot re-attribute a `confirmed` row, and is idempotent via both destination unique keys. It is deliberately **not** gated on `nrow(vario_original) > 0`: an assertion row lives independently of the review's connect snapshot and can exist when that snapshot is empty. Registered immediately **after** `functions/variation-provenance-reconcile.R` in `load_modules.R`; keep that order.
- **Correctness is server-side, never client-side.** Three independent frontend surfaces prefill and resubmit variation terms — `app/src/views/curate/composables/useEntityInfo.ts` (ModifyEntity), `app/src/views/curate/composables/useReviewForm.ts` (the Review page's Edit-Review modal), and `app/src/composables/review/useReviewApprovalActions.ts` (ApproveReview) — so a design that depends on one new UI sending the right signal leaves the others laundering. Never trust a client field; in particular **never reintroduce a client-sent rejected-terms array** (an earlier design revision did, and existing clients never send it). Omission from the submitted set *is* the rejection. `provenance_action` is read off the **raw** submission by `review_write_extract_provenance_actions()` *before* normalization, because `review_write_normalize_ontology()` reduces each term to `(vario_id, modifier_id)` for the connect-table write and would drop any extra field.
- **The curation three-zone picker is on one surface only.** `ReviewFormFields.vue` + `useVariationProvenanceZones.ts` (Confirmed / Needs confirmation / Suggested, modifier shown per card, inline evidence) is consumed **only** by `app/src/views/review/components/ReviewEditModal.vue` on `views/review/Review.vue` — **not** by `ModifyEntity.vue`, which uses a different review form (`InlineEntityWorkflow.vue` / `CombinedStatusReviewWorkflow.vue` bound to `useEntityInfo`'s `select_variation`). `ModifyEntity.vue` and `ApproveReview.vue` therefore still prefill without the deliberate-act UI and are protected **server-side** instead. All four surfaces now parse tags with `splitOntologyTag()` (#611 closed the two that still used `item.split('-')[1]`/`const [prefix, id] = item.split('-')`, which truncate a hyphenated CURIE).
- **Read surface.** `GET /api/entity/<id>/variation` gains a per-term `provenance` object (`{state, max_strength, sources:[{source_type, source_key, strength, summary}]}`, `sources` ordered strength-desc with an unrecorded (`NULL`) strength last, then `source_key`-asc — produced in R, so ordering never depends on the driver) or `null`. `GET /api/entity/<id>/variation/<vario_id>/<modifier_id>/evidence` serves the full `evidence_json` plus a per-record `created_at` import date (#612 — see the note below); `GET /api/entity/<id>/variation/suggestions` is **Curator**-gated and must stay **declared before** any dynamic `/<sysndd_id>/variation/<...>` sibling or `suggestions` is captured as a `vario_id` (the `/status/_list` shadowing lesson). All three are DB-only, add **one** query per request (never per term), bind their params rather than interpolating, and enforce entity visibility inside the same statement via `JOIN ndd_entity_view`. The public reads are state-gated to `('active_unconfirmed','confirmed')` so a public route cannot leak `suggested`/`rejected` curation workflow state — which is why the Curator-gated suggestions route inlines the full evidence records instead. There is deliberately **no `tryCatch`** around the provenance read: a swallowed failure would render every term as `provenance: null`, i.e. present machine-derived annotations as curator-authored.
- **Static guard:** `api/tests/testthat/test-unit-variation-connect-write-guard.R` scans `api/functions/`, `api/services/` and `api/endpoints/` and fails if any file outside the allowlist (`functions/ontology-repository.R`, the sole entry) co-locates an `INSERT`/`UPDATE`/`DELETE`/`REPLACE`/`TRUNCATE` with `ndd_review_variation_ontology_connect`, and separately asserts `review-write-service.R` still calls `variation_provenance_reconcile_for_review(..., conn = txn_conn)`. A third guard keeps four **deleted** helpers deleted (#612): `svc_review_add_variation_ontology()` / `put_post_db_var_ont_con()` and their equally-dead phenotype siblings `svc_review_add_phenotypes()` / `put_post_db_phen_con()` were removed from `api/services/review-service.R` after a repo-wide grep (including dynamic dispatch by name) found zero callers. They mattered because they delegate to the sanctioned repository functions **by name** rather than embedding SQL, so they passed the text guard while bypassing `review_write_mutate()` — writing the connect table with no reconciliation and silently reintroducing the laundering bug. A resurrection is legitimate only if it routes through `review_write_mutate()`.
- **Evidence import date (#612).** Both the evidence route and the Curator suggestions route select `e.created_at AS evidence_created_at` — **aliased**, because the suggestions query also selects the assertion's own `a.created_at` and two same-named columns collide in one result set. They share `.svc_vp_evidence_records()`, so **both** queries must select it: a caller that forgets it does not degrade to a missing field, it errors (`NULL[[i]]` → "subscript out of bounds"), which is the intended direction. The column is a MySQL `DATETIME` and carries **no timezone**, so it is serialized with **no zone designator** (`"YYYY-MM-DDTHH:MM:SS"`) and the frontend's `formatImportedDate()` (`app/src/views/pages/components/variationProvenance.ts`) reads the calendar fields off the leading `YYYY-MM-DD` **literally** rather than parsing an instant — `new Date(...)` would have the engine assume a timezone and could shift the displayed day. The dialog's "Imported" line is assembled by `importedLineParts()` as date · batch · release, each part independently omitted when null, and the row disappears entirely when all three are.
- **`origin_review_id` (migration `049`) records which review an import wrote to — and nothing reads it yet.** Additive, nullable, and deliberately **without** an FK to `ndd_entity_review`: it is a historical audit fact ("the import wrote to review N"), which stays true after that review is deleted or superseded, so an FK would make the audit trail cascade-deletable or block the delete outright; it also avoids taking a shared parent-row lock for each of the ~8,083 evidence rows the backfill inserts. It is a **column and not an `evidence_json` key** because the hot read path (`functions/variation-provenance-repository.R`) never selects `evidence_json`, so a JSON key would be reachable only one assertion at a time from the evidence-detail endpoint, whereas a column makes "which imported terms have **moved**" — i.e. now rest on a later curator review while the underlying machine evidence is unchanged — a single indexed join. No `api/` or `app/` code selects it today; it is Phase-6 fuel, parked deliberately under #612 rather than orphaned. Only `test-unit-evidence-origin-review.R` references it.

- **Register new provenance modules in `api/bootstrap/load_modules.R`** — files are not autodiscovered, and the single loader covers both the API and the durable worker. Current entries: `functions/variation-provenance-evidence.R`, `functions/variation-provenance-repository.R`, `functions/variation-provenance-reconcile.R`, `functions/variation-provenance-carry-forward.R`, `functions/variation-provenance-approval.R` (in that order), and `services/entity-variation-provenance-service.R` → `services/curate-variation-suggestion-service.R` → `services/curate-variation-apply-service.R` immediately **before** `services/entity-read-endpoint-service.R`. The two `curate-variation-*` services reuse `.svc_vp_na_to_null()` / `.svc_vp_evidence_order()` / `.svc_vp_max_strength()` from the entity service, so they must load after it.
