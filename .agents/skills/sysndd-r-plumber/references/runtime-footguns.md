# R / Plumber / DBI runtime footguns

> Extracted verbatim from `AGENTS.md` (2026-09-01) to keep the root instruction file lean.
> This is the authoritative detail for these rules.

- Namespace `dplyr::select(...)` and similar verbs explicitly in API code. Several loaded packages mask them: `biomaRt` exports an S4 `select` and `stats` exports `filter`, so whether a bare call resolves to the dplyr verb depends on package ATTACH ORDER — which differs between the running API, the durable worker, the mirai pool and a standalone `Rscript`. A bare call fails with `unable to find an inherited method for function 'select' for signature 'x = "tbl_df"'`, which is exactly how `gen_mca_clust_obj()` broke the moment it was exercised outside the API's own load order. All of `api/{functions,services,endpoints,core}` is now fully namespaced for `select`/`filter`, and `api/tests/testthat/test-unit-dplyr-namespace-guard.R` fails if a bare call reappears.
- Loaded packages also mask **base** functions in the API/worker global search path, so a bare base call can fail at runtime even though it parses fine. The `config` package (loaded for DB config) masks `base::get` with a signature `get(value, config, file, use_parent)` that has **no `mode` argument** — so `get(name, mode = "function")` raises `unused argument (mode = "function")` (note `exists(name, mode = "function")` is *not* masked, so the two are asymmetric). Use `base::get(...)` explicitly, or dispatch to the concrete function by name instead of `get()`. This failed **every** cluster-snapshot refresh in #514 and was only caught by live end-to-end verification (host R did not mask it — it manifests only in the fully-loaded API/worker env). Same family as the masked `merge()` (use `dplyr::*_join`) and `biomaRt::select` shadowing `dplyr::select`.
- Use `inherits(x, "Date")`, not `is.Date(x)`, in library-light contexts.
- Plumber may return JSON scalars as arrays. Frontend callers should unwrap values before feeding them back into axios params.
- **Plumber parses a request body with `jsonlite::fromJSON(simplifyVector = TRUE)`, so a uniform JSON array of objects arrives as a `data.frame`, not a list of records.** `req$argsBody$items[[1]]` is then the first COLUMN — an atomic vector — and `length()` counts columns, not items. Any handler that iterates a body array must accept both shapes; `review_write_provenance_records()` (`services/review-write-service.R`) and `.svc_cva_normalize_items()` (`services/curate-variation-apply-service.R`) both do it with the same `lapply(seq_len(nrow(x)), \(i) as.list(x[i, , drop = FALSE]))`. This is the same trap as the force-apply payload tables (`functions/async-job-force-apply-payload.R`), and it shipped once already: the curation queue's `confirm`/`dismiss` rejected **every** well-formed batch with `items[1] must be an object.` A test that hand-builds `req$argsBody` as a list of lists is testing the `simplifyVector = FALSE` shape and will stay green — drive the parse (`jsonlite::fromJSON(jsonlite::toJSON(...))`) or drive real HTTP. Note a non-uniform array (mixed types) does NOT collapse, so it still arrives as a list; both paths need to work.
- A route that serves a **list-column** whose elements may be `NULL` must declare `@serializer json list(na="string", null="null")`. Without `null="null"`, `jsonlite::toJSON()` renders a `NULL` list element as `{}`, not `null` — which silently breaks any "the field is `null` when absent" contract (it nearly shipped that way on `GET /api/entity/<id>/variation`, whose `provenance: null` *is* the "curator-authored" contract, #608). Conversely, `na="string"` renders an `NA_integer_` **nested inside a list** as the literal string `"NA"`, so normalize nested `NA` scalars to `NULL` in the service and let `null="null"` render them as JSON `null`. `null="null"` has no effect on ordinary `NA` data-frame columns, so adding it to an existing route leaves the `na="string"` behaviour of scalar columns untouched. Plumber still does not auto-unbox, so scalars nested inside a list serialize as length-1 arrays — unwrap them field-by-field on the client (`unwrapValue()`), never blanket-recursively, or genuine length-1 arrays get flattened. Plumber also does **not** percent-decode path parameters: an `encodeURIComponent`'d CURIE arrives verbatim as `VariO%3A0017`, so a route taking a CURIE path segment must `utils::URLdecode()` defensively (a malformed escape only *warns*, so convert that warning into a 400).
- The `literature` → publications parse lives in `api/functions/review-literature-parsing.R`, not inline in the endpoint, because its `publication_type` comes from `dplyr::bind_rows(.id = )` — which labels rows by the **position** of the frame they came from (`"1"` additional references, `"2"` GeneReviews), not by anything in the data. A zero-row first frame must not shift the second frame's label to `"1"`, or clearing every additional reference would silently re-file the surviving GeneReviews as additional references. It does not, but only `test-unit-review-literature-parsing.R` says so. Note that a zero-row result is the **destructive** case, not a no-op: `review_write_mutate()` routes it on PUT to `publication_replace_for_review()` with an empty tibble, i.e. delete them all — which is exactly what the browser sends when a curator clears the field.
- Plumber does not propagate a router's error handler to mounted sub-routers. Every endpoint file is mounted as its own sub-router in `api/bootstrap/mount_endpoints.R`, so each must be wrapped with the `mount_endpoint()` helper (which attaches the RFC 9457 `errorHandler` from `api/core/filters.R`). Without it, a thrown classed error (e.g. `stop_for_bad_request()` → `error_400`) falls back to plumber's opaque default `{"error":"500 ..."}` instead of mapping to the correct status + `application/problem+json`. Never reintroduce a bare `plumber::pr_mount("/api/x", plumber::pr("endpoints/x.R"))`; route it through `mount_endpoint()`, which attaches both `pr_set_error(errorHandler)` and `pr_set_404(notFoundHandler)`. Only `error_400/401/403/404/500` classes exist. The frontend reads problem+json via `extractApiErrorMessage` (`app/src/utils/api-errors.ts`, `detail` → `title`). Static guard: `api/tests/testthat/test-unit-endpoint-error-handler.R`.
- `DBI::dbBind()` with `?` placeholders needs `unname(params)`; named lists can fail silently.
